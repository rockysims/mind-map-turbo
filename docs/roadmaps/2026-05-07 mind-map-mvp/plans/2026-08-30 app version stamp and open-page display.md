# Plan: App version stamp and Open-page display

**Created:** 2026-08-30
**Author:** Claude agent
**Milestone:** none — contained follow-up on
[milestone 04l](../milestones/04l-self-contained-html-save-files.md),
[milestone 04m](../milestones/04m-single-document-save-ux.md) and

**Status:** draft
**Total estimated effort:** M

## Summary

Give every self-contained `.html` document an orderable stamp of the app build
inside it, show that stamp on the Open page, and warn when a graph is opened
into an app older than the one that last wrote it. Closes the "faint grey
version number" item in `docs/roadmaps/TODO.md`.

## The problem this solves

The stated need is "when upgrading an old graph to a new version, tell which
`.html` file is newer". File modification time cannot answer that, and answers
it wrongly with confidence: Download from an old `.html` reuses _that file's_
app code as the export shell (`exportHtmlShell()` prefers the captured shell,
`+page.svelte`), so the result is a **fresh mtime wrapped around an old app**.
Sorting a folder by date actively misleads.

Two thirds of the machinery already exists and is unused for this:

- `<meta name="mind-map-offline-shell-source">` (`scripts/offline-shell-fingerprint.mjs`)
  is in every built shell and therefore in every downloaded document. It
  identifies a build exactly, but it is a content hash — **not orderable** —
  and it is never surfaced.
- `exportedAt` (`graphFile.ts`) records when a file was _saved_, which says
  nothing about which app wrote it.
- `minReaderVersion` → `unsupported-app-version` → open-in-new-tab
  (`graphPersistenceController.ts`) already handles "this file is too new for
  me", but only fires on a hard format bump, never on ordinary app age.

The gap is narrow: an **orderable** stamp, one place to read it, and a warning
that fires on the one dangerous direction.

## Open questions resolved

- **What the version string is.** **HEAD's commit date plus its short SHA**,
  stored as `<iso-instant> <short-sha>[-dirty]` and displayed as
  `2026-08-29 12:47 · 0785c93`. Date orders itself with zero maintenance;
  `package.json` has sat at `0.0.1` with no bump discipline, so semver would be
  a lie the first time someone forgot.

- **Commit date, not wall-clock build time.** **Commit date**, because it names
  _which code_ is in the file — and "which app is this" is exactly the question
  the stamp exists to answer. A build clock only records when someone ran a
  command. Anchoring to a commit is also what makes the `-dirty` flag mean
  anything: it says "this build contains work that is not in that commit".

  This was originally justified by git churn — the claim that a wall-clock stamp
  would dirty the tracked 581 KB shell on every build. **That was wrong, and is
  recorded here so nobody re-derives it.** The shell already churns on every
  build: SvelteKit randomizes its client global namespace per build
  (`__sveltekit_1014tg8` → `__sveltekit_n5nfo0`) and defaults `version.name` to
  `Date.now()`. Two consecutive builds of identical source differ in three
  places today, so the stamp cannot make reproducibility worse — there is none
  to lose.

- **Where it is displayed.** **The Open page only
  (`filePickerTabHtml` in `browserGraphFile.ts`), as a faint second line under
  the `Open graph file` heading.** Every canvas corner already has a claimant —
  `GraphQueryPanel` and the focus breadcrumbs are both top-left, the focus close
  button is top-right, Find/Filter is bottom-left, the tag legend is
  bottom-right — so a chip there would need conditional hiding against two other
  overlays. The Open page is the one screen that exists purely for file
  wrangling, so the version is on-topic there instead of being clutter parked on
  the graph. The canvas is not touched at all.

- **What the Open page's version refers to.** **The app you are currently
  running**, not the file about to be picked — that page is generated by the
  running app before any file is read. It does not by itself answer "which of
  these two files is newer"; `grep mind-map-build *.html` answers that from a
  terminal without opening anything, and T05's warning covers the case that
  actually bites.

- **Whether the Open page compares against the picked file.** **No.** That page
  already reads the whole file before navigating, so it could — but it is a
  `document.write` template string with hand-written inline JS, reachable only
  by e2e. The same warning app-side rides the existing notice machinery, is a
  pure testable function, and lands a few hundred milliseconds later in what is
  one continuous flow. Duplicating the comparison rule into a string blob to
  save that is a bad trade.

- **How the warning knows who wrote a file.** **A new optional `appVersion` on
  the export payload**, not a re-scan of the file's `<meta>`. It is semantically
  the right field ("the app that wrote this graph"), it survives the JSON export
  path which has no HTML at all, and it compares already-parsed data instead of
  re-regexing a 581 KB string.

- **Whether that needs a schema bump.** **No.** `unwrapPersistedGraph`
  validates `schemaVersion` and `data` and ignores unknown top-level keys —
  `documentId`, `exportedAt`, `htmlDocumentVersion` and `minReaderVersion`
  already sit there. Old readers ignore `appVersion`; new readers treat it as
  optional. `CURRENT_SCHEMA_VERSION` stays at 6.

- **What dev mode shows.** **`version dev`.** The dev server serves no build
  meta, so there is no honest version to show. Worth knowing about the sharp
  edge rather than papering over it: in dev the Open page reads `dev` while
  Download packages the _last built_ `static/offline-app-shell.html`, which is
  exactly the mismatch `pnpm check:offline-shell` already exists to catch.

## Out of scope (for this plan)

- Any version indicator on the graph canvas — no corner chip, no toolbar line.
- Changing the download filename, the app's `<title>`, or the Open page's tab title.
- Comparing versions on the Open page before navigating (see above).
- Semver, release tagging, or a changelog.
- A Settings/About dialog (still unbuilt; this plan must not depend on it).
- Retrofitting already-downloaded files, which carry no stamp and never will.
- Rewriting `controllerNotice`'s substring-based priority list (see Risks).

## Tasks

### T01 — Generate the build stamp and inject it into the offline shell

|                |                                                                                                           |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| **Depends on** | —                                                                                                         |
| **Wave**       | 1                                                                                                         |
| **Agent**      | fast/cheap                                                                                                |
| **Effort**     | S                                                                                                         |
| **Files**      | new `scripts/build-stamp.mjs`, `scripts/inline-static-build.mjs`, `scripts/offline-shell-fingerprint.mjs` |
| **PR title**   | `feat(build): stamp the offline shell with its source commit`                                             |

New module mirroring the shape of `scripts/offline-shell-fingerprint.mjs`:
export `BUILD_STAMP_META_NAME = 'mind-map-build'`, `resolveBuildStamp({ repoRoot })`,
`withBuildStamp(html, stamp)` and `readBuildStamp(html)`.

`resolveBuildStamp` shells out to git for HEAD's committer date
(`git log -1 --format=%cI`, normalized to a `Z` instant), the short SHA
(`git rev-parse --short HEAD`), and dirtiness (`git status --porcelain`),
producing `2026-08-29T19:47:26Z 0785c93` or `... 0785c93-dirty`. If git is
absent or fails, fall back to the build clock so a tarball build still produces
something — never throw.

Call it from `inline-static-build.mjs` alongside the existing
`withOfflineShellFingerprint` call, so the meta lands in both `build/index.html`
and `static/offline-app-shell.html`.

Add `scripts/build-stamp.mjs` to `appInputs` in
`scripts/offline-shell-fingerprint.mjs`. That list enumerates build inputs by
hand, so without this an edit to the new script would leave the freshness gate
reporting a stale shell as fresh.

**Acceptance**

- `pnpm --filter mind-map-sv build` emits
  `<meta name="mind-map-build" content="...">` into both outputs.
- Two builds of the same commit emit the **same stamp value**. Not the same
  shell — see the churn note above; that difference is SvelteKit's, not ours.
- Editing `scripts/build-stamp.mjs` alone changes the source fingerprint.
- `pnpm check:offline-shell` still passes (the meta is injected into output, so
  it does not feed back into the source fingerprint).
- A build with an uncommitted edit produces a `-dirty` suffix.

### T02 — `buildInfo.ts`: parse, format, and compare build stamps

|                |                                                             |
| -------------- | ----------------------------------------------------------- |
| **Depends on** | T01                                                         |
| **Wave**       | 2                                                           |
| **Agent**      | default                                                     |
| **Effort**     | S                                                           |
| **Files**      | new `src/lib/buildInfo.ts`, new `src/lib/buildInfo.spec.ts` |
| **PR title**   | `feat(build-info): pure build stamp parsing and comparison` |

Pure module, no DOM:

- `parseBuildStamp(content: string | null): BuildStamp | null` →
  `{ iso, commit, dirty }`, null for anything unparseable.
- `formatBuildStamp(stamp: BuildStamp | null): string` →
  `2026-08-29 19:47 · 0785c93` (or `...-dirty`), and `dev` for null. Renders the
  stored instant verbatim with **no timezone conversion**, so what the UI shows
  and what `grep` shows are recognisably the same value.
- `compareBuildStamps(a, b): number | null` — null when either side is
  unorderable, so callers cannot accidentally treat "unknown" as "older".

Pin the meta name against the build script the way
`src/lib/vendor/temmlVersion.spec.ts` pins the vendored temml version: import
`BUILD_STAMP_META_NAME` from `../../scripts/build-stamp.mjs` and assert the two
constants agree, so the duplication cannot silently drift.

**Acceptance**

- Spec covers: a well-formed stamp, a dirty stamp, `null`, empty string,
  garbage, and a stamp missing the SHA.
- `compareBuildStamps` returns null when either side is null or unparseable, and
  orders correctly otherwise (including equal).
- The meta-name pinning spec fails if either constant is edited alone.

### T05 — Warn when a file was written by a newer app

|                |                                                                                                                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Depends on** | T04                                                                                                                                                                                                                  |
| **Wave**       | 5                                                                                                                                                                                                                    |
| **Agent**      | default                                                                                                                                                                                                              |
| **Effort**     | M                                                                                                                                                                                                                    |
| **Files**      | `src/lib/buildInfo.ts`, `src/lib/buildInfo.spec.ts`, `src/lib/graphPersistenceController.ts`, `src/lib/graphPersistenceController.spec.ts`, `src/lib/components/ui/GraphPersistence/GraphPersistence.stories.svelte` |
| **PR title**   | `feat(persistence): warn when a graph comes from a newer app version`                                                                                                                                                |

Pure `newerAppNotice(fileVersion, appVersion): string | null` in `buildInfo.ts`,
returning `Saved by a newer app (2026-09-15 10:02).` only when both stamps are
orderable and the file's is strictly newer — null otherwise, so an unknown
version is never reported as stale.

Wire it into `loadEmbeddedDocument`, which is the real load path for both the
picker and for opening a downloaded `.html` directly, and into
`importGraphDocument` for parity. Emit it as
`status: { state: 'notice', message }`.

Note the two cases that must _not_ fire: opening a downloaded file directly
compares a document against its own shell and is always equal, and opening an
older file — the ordinary upgrade direction, which works fine — is silent. The
warning exists for exactly one case: opening a newer file into an older app,
where the next Download silently wraps a new graph in old app code.

**Acceptance**

- Spec: newer file → notice; older file → no notice; equal → no notice; either
  side `dev`/unparseable → no notice.
- Spec pins that the message survives `controllerNotice` and is not overwritten
  by `documentStatusNotice` (see Risks).
- A `GraphPersistence` story exercises the newer-file import through
  `PersistedGraphHarness` and asserts the surfaced notice via the harness's
  `data-last-*` attributes.
- The "Local edits found" conflict flow still behaves as before.

## Wave plan

```
Wave 1   T01   build stamp generation
Wave 2   T02   pure parse/format/compare (pins T01's constant)
Wave 3   T03   Open page display (establishes the +page.svelte seam)
Wave 4   T04   appVersion on the payload (reuses that seam)
Wave 5   T05   newer-app warning

```

Deliberately sequential rather than fake-parallel: T03 and T04 both need "the
running app's version" in `+page.svelte`, and T04/T05 share `graphFile.ts` and
the controller. If a single agent carries T04 and T05, they can land as one PR —
the warning is meaningless without the stamp.

Each of T01–T03 is independently shippable: T01 alone already makes
`grep mind-map-build *.html` answer the original question from a terminal.

## Risks and rollback

- **`controllerNotice` prioritises notices by substring match** — it surfaces a
  notice over the document status only if the message contains `failed`, `newer`
  or `Kept local draft` (`graphPersistenceController.ts`). T05's copy happens to
  contain "newer", so it surfaces by coincidence of wording. That is fragile.
  Pin it with a spec rather than relying on it, and leave the predicate itself
  alone — reworking it is a separate change with its own regression surface.

- **The toolbar status line is `white-space: nowrap`** inside a
  `max-width: calc(100vw - 1.5rem)` pill (`GraphToolbar.svelte`), so a long
  message clips on narrow screens. `Saved by a newer app (2026-09-15 10:02).` is
  sized to fit; do not let it grow. The existing TODO about splitting that status
  onto two lines would relieve this properly and is not in scope here.

- **T06's shell diff is ~581 KB.** Expected and unavoidable; it is why it gets
  its own commit. Reviewers should read the other five commits and skim this one.

- **The stamp records the commit the shell was built _from_, not the commit that
  contains the shell.** T06's shell will name T05's commit. This is correct — the
  stamp describes the code inside the file — but it looks off-by-one at a glance
  and is worth a sentence in the commit body.

- **No-git builds fall back to the build clock**, which reintroduces per-build
  churn in that environment only. Acceptable: the repo's own workflow always
  builds from a clean checkout.

- **If the commit-date approach proves wrong**, T01 is the only task to revisit;
  `buildInfo.ts` parses an instant and a SHA regardless of where they came from,
  and nothing downstream cares.
